# Stored state and its format

berth keeps state in files and in Docker labels, and a later build reads it
back. This note says which of it carries a format version, where the version
lives, what a build does with a version it does not know, and how a change to a
store adds a migration. The code is `internal/stateformat`; every number below
is a constant there, pinned by its tests.

## Rules

1. **Every store berth reads back says which format wrote it.** The version is
   a whole number. Each store has its own counter, not a berth release number,
   and a counter changes only when that store's shape does.
2. **A build refuses state of a newer format.** It does not read, repair,
   rewrite or delete it (see "The refusal"). The one exception is the index
   card, which is regenerated by every `up` and decides nothing: a card of any
   other version reads as no card.
3. **State with no version, or one this build never wrote, is not state berth
   wrote.** It is malformed or foreign, and each store reacts as it does to any
   other file it cannot read (see "Missing or unknown version"). A version is
   never assumed.
4. **A version is judged before the rest of the shape.** A newer format may
   have changed everything else, so the version is read on its own (a JSON
   document's top-level `version`, the first line of a marker) and a newer one
   is refused as newer, not reported as corrupt.
5. **Refusing is not clearing.** No format check removes or rewrites state, takes
   a lock early, or skips proof of ownership.

## Inventory

| State | Where | Version |
| --- | --- | --- |
| Control home | `<control home>/.berth-control-home` | the file says `format 2` |
| Identity markers | `<git dir>/berth/worktree-id`, `<git common dir>/berth/repository-id` | first line `format 1`, then the UUID |
| Registrations (with each worktree's port pins, host routes and label namespace) | `<control home>/repositories/<repo>/worktrees/<worktree>.json` | `"version": 1` |
| Shared-service records (with their port pins) | `<control home>/repositories/<repo>/shared/<name>.json` | `"version": 1` |
| Router state | `<berth root>/router/state.json` | `"version": 1` |
| Lock holder records | `<lock file>.holder` | `"version": 1` |
| Index card | `<worktree home>/index.json` | `"version": 1` |
| Docker labels on containers, networks and images of a worktree or a shared stack | `dev.berth.format` | the label's value, `1` |
| Router containers | `dev.berth.router-protocol` | the protocol number, its own counter |
| Shared definition hash | `dev.berth.shared-definition` | the `v1:` prefix, the hash scheme's counter |
| Named volumes | none | proven by the ownership labels alone |
| Route files, router stack file, index page, override files | `<berth root>/router/…`, `<worktree home>/berth.override.yaml`, `<repo>/shared/berth.override.yaml` | none: derived |
| Relocated copies | `<control home>/bin/<sha256>` | none: the name is the version |
| Backup bundles | where `backup` was told | none: the hook's |
| `settings.toml`, `berth.toml` | the berth root, the repository | none: user-written |
| Quarantined homes | `<repo>/instances/.deleting-<worktree>` | none: a renamed home |

### Why each is, or is not, versioned

**Control home.** The marker says `format 2` and berth refuses a directory
whose marker holds anything else. 2 is the current version: the marker's bytes
are a storage name (`CONTRIBUTING.md`), written into every control home, so the
number changes only through a migration that updates existing control homes
before it writes the new marker (see "Adding a migration"). The other counters
start at 1. The marker's bytes never vary by writer (no PID, no
timestamp), because `writeMarkerRacingCreators` adopts a racing creator's
marker on that basis.

**Identity markers.** Nothing else ties a checkout to its registrations, so
the markers carry the version themselves. A marker is two lines, so no reader
can take its first line for a UUID.

**Registrations, shared records, router state.** JSON documents with a
top-level `version`. Port pins, host routes and the label namespace are fields
of the records, not stores of their own, and take their version.

**Lock holder records.** The `.holder` sidecar names the process that holds
a lock and is read to judge whether that holder is gone. A record of a newer
format names no holder this build can identify, so the holder is judged
**unverifiable**: an acquirer refuses it, with the refusal below, until
`worktree unlock --holder-unverifiable` (or the registry or router form) clears
it. This holds even for a record the newer berth marked released: this build
cannot read the release, so a lock a newer berth used needs `worktree unlock`.
A record with no version is no record: there is nothing to recover, and the
lock is taken once the flock is free. The lock file itself is empty.

**Index card.** See rule 2.

**Docker labels.** `dev.berth.format` is stamped by the code that stamps
`managed`, `repository-uuid` and `worktree-uuid`, on every container and network
a worktree's Compose file creates, every image its build produces, and every
container and network of a repository's shared stack. It is `1`. The router's
containers carry `dev.berth.router-protocol` instead (routing.md, decision 10),
which has its own newer-berth rule: a running router at a higher protocol is
refused and never downgraded. The shared definition hash's `v1:` prefix versions
the hash scheme; a changed scheme reads as drift (routing.md, decision 16).

**Named volumes carry no format label.** Compose treats a changed label on an
existing named volume as drift and asks "Recreate (data will be lost)?". With
no terminal the answer is no and the volume keeps its old labels; with `--yes`
it loses the data. A label on a volume can therefore never be added or changed
safely, so a volume is proven by the three ownership labels, as an anonymous
volume is, and its format is that of the containers and records around it. This
applies to the worktree's volumes and the shared stack's alike.

The registration is the gate for a worktree's volumes: `worktree remove` and
`down` need it, and they refuse a newer registration before any volume is
reached. A change to what the ownership labels mean must therefore ride a
registration bump. A volume is proven by its ownership labels alone.

Containers are recreated and networks silently replaced when their labels
change, so a future `DockerLabel` bump restarts the services of every worktree
on its next `up`. The network recreate fails if a shared container is attached
to it, as any label bump does; the recovery is `berth down` then `berth up`,
and this is expected on a label bump.

**Compose never prompts.** `up`, `down` and the shared stack's commands run
Compose without a terminal: none is `Interactive` (the only mode that hands a
child this process's stdin), a nil `Input` gives the child `/dev/null`, and
none passes `--yes`. A question about a changed label therefore cannot hang or
be answered; `TestComposeNeverPrompts` pins it for `up` and `down`. Only the log
follower is `Interactive`.

**Derived files.** Traefik and Compose read them, so they cannot carry berth
keys. They are written from versioned state and rewritten by the next `up` or
repair; a route file whose contents berth does not recognise is never trusted.

**Relocated copies, backup bundles.** An entry is named by the sha256 of its
bytes; a bundle's contents belong to the project's hook (`docs/hooks.md`).

**`settings.toml`, `berth.toml`.** They are written by people and validated
against a schema that rejects unknown keys (`docs/design/config.md`). A key a
newer berth added is refused as an unknown key, naming the file.

## The refusal

Every store that finds a newer version refuses with one message:

```
Refusing to <use|touch> <what, with its path or ID>: it is format <found>, written by a newer berth, and this build reads format <supported>. Upgrade berth, then run this again.
```

For example:

```
Refusing to use the router state /home/me/.berth/router/state.json: it is format 2, written by a newer berth, and this build reads format 1. Upgrade berth, then run this again.
Refusing to touch the container 4f1c… (service api): it is format 2, written by a newer berth, and this build reads format 1. Upgrade berth, then run this again.
Not taking the worktree main lock: its holder record is format 2, written by a newer berth, and this build reads format 1. Upgrade berth, then run this again.
```

It names the store (with its path or ID), the version found, the version this
build reads, and what to do. On the clearing path (`worktree unlock`) the lock's
refusal also offers `--holder-unverifiable`; an ordinary acquirer's does not. It exits 1 like any expected failure
(`stateformat.Newer`) and never says to delete the state, which a newer berth
still needs.

| Store | What refuses | Subject |
| --- | --- | --- |
| Control home | `files.SecureControlDirectories`, so every command that writes under it | `the control home <path>` |
| Identity markers | `IdentityService` reads | `the identity marker <path>` |
| Registrations | `Store.Find`, `Initialization` and every writer; `Scan` reports the file as a problem | `the registration <path>` |
| Shared records | `Store.FindShared` and every writer; `SharedRecords` reports a problem | `the shared-service record <path>` |
| Router state | `router.ReadState`, so `Ensure`, `CheckPorts` and port allocation | `the router state <path>` |
| Lock holder records | taking, clearing and describing a lock | the lock's refusal, above |
| Docker containers, networks, images | `Inventory`, `Reap` and `ProveNetwork` (worktree), the shared stack's `verify` | `the container <id> (service <name>)`, `the network <id>`, … |

A newer registration also stops port allocation and hostname allocation while
it sits unread: a record this build cannot read may hold a port, so the
allocators refuse rather than guess. Their refusal tells the user to upgrade,
not to move the file aside.

### Docker: what is proven, and what refuses

The ownership labels prove who owns a resource only in the format they were
written in; a newer format may change what proves ownership. So a container,
network or image whose format label is newer than this build's is **not proven
owned**, and teardown refuses by the rule that applies to any resource whose
labels do not match. `Inventory` verifies every resource before any is
returned and `Reap` re-verifies each before removing it, so one such resource
refuses the whole teardown and nothing is removed. The resource is still
*found* by the three ownership labels (the listing filters leave the format
label out), so it is refused, not orphaned.

A resource with no format label, or one that is not a plain decimal number, is
not one this build stamped, and is refused the same way, with the action:

```
Refusing to touch the container 4f1c… (service api): its dev.berth.format label is missing or not recognised, so berth cannot prove it is this worktree's. After checking that nothing needs it, remove it with `docker container rm 4f1c…`.
```

The same proof gates a network connect or disconnect (`ProveNetwork`): an
unproven network is reported and never touched. A volume is proven without the
format label (above). Listing, status and the index only read, so they do not
check the format; in particular `VerifyConsumer`, which finds the containers
that use a shared service, counts any managed container regardless of its
format.

Before `compose up` (a worktree's `up`, and a shared stack's start), berth makes
one cheap check: a `docker ps -a` and a `docker network ls`, filtered by the
ownership labels and printing only each ID and its format label. A container or
network of a newer format refuses the start with the usual message, because the
override this build writes carries its own format label, which Compose reads as
a changed configuration and answers by recreating the resource. No inspect is
made and a full inventory is not taken on every `up`; a resource with a missing
label is not refused here, and is left to the proof at teardown so that `up`
never traps a project. Berth's other proof points are teardown, reap, connect
and disconnect.

## Missing or unknown version

| Store | Reaction |
| --- | --- |
| Control home | An empty marker alone in an otherwise empty directory is written. An empty marker beside other content is refused ("its marker … is empty but the directory already holds berth state"). Any other contents, a smaller number or text that is not exactly `format <n>` and a newline included, are refused as "not berth's own format" and never rewritten. |
| Identity markers | `Invalid identity marker: <file>. A marker is the line "format 1" and then the checkout's UUID. To start over, move the file aside: …` Never rewritten: the markers are the checkout's identity, and a guess would orphan its registration. |
| Registrations, shared records | `… has an unrecognized version or shape: <file>`: skipped by listings, refused by writers, and blocking port allocation. |
| Router state | `The router state <file> is not readable. Remove it and run this again; the router picks its ports afresh.` That advice is safe only for unreadable state, not newer, and the router re-picks its ports. |
| Lock holder record | No record: nothing to recover. |
| Index card | No card. |
| Container, network, image | Not proven owned (above). |

## `doctor`

Each store's check reports its own refusal as the line's detail, in the
section that covers it:

- **Registry / control home** fails with the control-home refusal
  (`files.AssertControlHomeFormat`, read-only), and **registrations** is then
  skipped ("control home not readable") instead of reading "none yet".
- **Registry / router state** reads `state.json` and fails with its refusal.
- **Registry / unreadable record** and **Shared services / unreadable record**
  carry the record's refusal; a newer shared record is not told to be moved
  aside.
- **This checkout / this worktree** carries an identity marker's refusal, once:
  the missing-checkouts scan that would repeat it is skipped.
- **Locks** warns for a lock whose record a newer berth wrote.

`doctor` does not look at Docker resources, so a container, network or image of
a newer format is reported by the command that tried to touch it.

## Adding a migration (a sketch)

Nothing here implements one.

1. **Raise the store's constant** in `internal/stateformat` and change the
   store's shape in the same change; the constants' test fails until the new
   number is written down on purpose.
2. **Write the step as a pure function** from the previous format's bytes to
   the new one's, in the store's own package. Readers accept N-1 and N: the
   current version is read, N-1 is migrated, a newer one is refused as above,
   anything else is foreign.
3. **Records migrate lazily and independently.** The first writer of a record
   under the registry lock rewrites it as N with `files.AtomicJSON`; a read-only
   command reads N-1 through the same function and writes nothing. Router state
   migrates the same way under the router lock. Identity markers migrate under
   the registry lock by an atomic rename of a new file, since a marker is read
   without a lock. The lock order does not change.
4. **The control-home marker bumps only on a layout change**, as an explicit
   eager step under the registry lock, with the marker written last, after
   everything it covers has moved, so every existing control home is updated
   before the new marker is written and an interrupted step is retried rather
   than half-believed. The marker is also what racing creators adopt, so a bump has to
   revisit `writeMarkerRacingCreators`.
5. **Docker labels cannot be rewritten on an existing resource**, and Compose
   treats a label change on a volume as data loss. A label migration therefore
   keeps accepting the previous value in the ownership proof; the accepted set
   only grows, and `up` stamps the new value on what it creates (recreating
   containers and networks). A resource is never inferred owned from a missing
   label.
6. **A storage-name change is a migration** (`CONTRIBUTING.md`): the same step
   reads the old name until it has run.
7. **Test it** with a fixture of the previous format in `testdata`, an upgrade
   test over it, and refusal tests for the new number. A change that cannot
   migrate refuses instead, in the words of the refusal above.
